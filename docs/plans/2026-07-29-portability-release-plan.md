# Plan: Portability release (ADR-0012) — compile everywhere, actuate where it can

**Date:** 2026-07-29 · **Source:** the apogee-side integration grill (owner, 2026-07-29) — apogee's `make check` runs on Linux and keeps a Windows cross-build green, so the v1.6.0 facade is unimportable by its first client's CI.
**Design authority:** [ADR-0012](../adr/0012-the-library-compiles-everywhere-and-actuates-where-it-can.md) (written in the same session as this plan). The client-side plan is `docs/plans/2026-07-29 - 00 - llama-launcher-integration-plan.md` *in the apogee repo*; its item 2 blocks on this plan's release item.

**Conventions for every code item:** follow the `coding-standards` skill; no AI attribution anywhere; CHANGELOG + TDD + README updates are collected in Item 5. The core rule, inherited from the facade plan: **darwin behaviour must not change** — the CLI's output and the facade's darwin semantics stay byte-identical; this plan moves code behind build tags, it does not redesign it.

**Resolved decisions (context for implementers):**

1. **Platform contract (ADR-0012):** darwin full · linux full · windows compiles + HTTP-actuated verbs work, unix-process paths return the new `ErrUnsupported`.
2. **Seam shape:** per-OS files with build tags — a `unix` tag shares darwin+linux process control; windows gets stubs. No `runtime.GOOS` branching in shared code paths.
3. **Two new facade sentinels:** `ErrUnsupported` (the windows stubs) and `ErrStartupTimeout` (the activation health-wait timeout, so a client can attach "may still come up" handling). Strict semver would call new exported API a minor; **owner call 2026-07-29: the release is v1.6.1** — the 1.6.x line includes the facade's architectural changes (portability completes importability; ADR-0012 records the reasoning).
4. **Verification floor:** the repo gains a cross-compile gate (GOOS linux/windows/darwin) and the layer-1 tests must pass **natively on linux** (they are httptest/tempdir-only — this plan makes that claim checkable for the first time).

## Part A — Per-OS seams (behaviour-preserving on darwin)

- [x] **1. Process control behind a `unix` seam** — ✅ DONE (2026-07-29) — `internal/launcher/server.go`, `internal/launcher/backend_ollama.go`, new `internal/launcher/process_unix.go` + `internal/launcher/process_windows.go`
  - `process_unix.go` (`//go:build unix`): `detachedSysProcAttr() *syscall.SysProcAttr` returning `{Setsid: true}`; `signalPID(pid int, sig …) error` and `signalGroup(pid int, …) error` wrapping today's `syscall.Kill(pid, …)` / `syscall.Kill(-pid, …)` calls verbatim (the SIGTERM→SIGKILL escalation in `terminatePID`, `server.go:253-289`, and the legacy-cleanup kill at `server.go:977`).
  - `process_windows.go` (`//go:build windows`): the same signatures; `detachedSysProcAttr` returns `nil` (harmless — the fork paths error before use), every signal func returns an error wrapping the internal unsupported sentinel (Item 3 exports it). `terminatePID` on windows therefore fails fast with that error rather than a build failure.
  - Rewire the five sites: `server.go:74` and `backend_ollama.go:109` (`SysProcAttr: detachedSysProcAttr()`), the three `syscall.Kill` sites through the wrappers. `startManagedServer` and ollama's `TryStart` gain an early windows guard returning the unsupported error (fork-then-fail would leak a child with no process-group control).
  - Tests: existing darwin/linux tests unchanged and green natively on linux (this item is what makes that possible together with Item 2); a windows-tagged compile check rides Item 4's gate (no windows test host — the stubs are error-return one-liners).
  - NOTES (2026-07-29): the early fork guard is a **fourth** seam function, `requireProcessControl() error` (nil on unix, wrapping `ErrUnsupported` on windows), rather than the three the item lists — a guard needs a per-OS answer and the plan's seam rule forbids `runtime.GOOS` branching in shared code. It is called first in `startManagedServer` and first in `(*Ollama).TryStart`.
  - NOTES (2026-07-29): the item's "legacy-cleanup kill at `server.go:977`" is the liveness probe `syscall.Kill(pid, 0)` in `IsProcessAlive` (line numbers drifted with Item 3); it now reads `signalPID(pid, 0) == nil`, so on windows `IsProcessAlive` is always false — correct there, since no PID-based path can act anyway.
  - NOTES (2026-07-29): the two single-process `proc.Signal(syscall.SIGTERM/SIGKILL)` calls in `terminatePID` were deliberately **not** routed through `signalPID` — they are `os.Process.Signal`, not `syscall.Kill` (the three sites the item names), they already compile on windows, and swapping them for a raw kill would change darwin behaviour. `terminatePID` still fails fast on windows: `IsProcessAlive` is false, so `stopServerAt` never calls it, and a direct call returns at the first `proc.Signal` error.
  - NOTES (2026-07-29): verified with a `-overlay` standing in for Item 2's `ui.go` poll — `GOOS=linux|windows|darwin go build ./...` all clean and `go test ./...` green natively on linux; without the overlay `GOOS=darwin go build ./... && go vet ./...` is clean. For Item 4: `GOOS=windows go vet ./...` still fails on **test** files (`server_test.go:1594` `Setsid`, and `integration_llamacpp_test.go` `syscall.Kill` under `-tags=integration`) — production code cross-builds everywhere, so the gate should scope its windows step accordingly.

- [x] **2. The menu poll behind per-OS files** — ✅ DONE (2026-07-29) — `internal/launcher/ui.go` → `internal/launcher/ui_poll_darwin.go`, `ui_poll_linux.go`, `ui_poll_windows.go`
  - Extract the `FdSet`/`Select` stdin-poll block (`ui.go:87-89` and its setup) into a single `pollStdin(…)` seam; darwin file keeps today's one-value form verbatim; linux file uses the two-value `n, err := syscall.Select(…)` form (the one-line fix the facade plan's Item 5 already prototyped via overlay); windows file returns "interactive menu is not supported on windows" — and `RunInteractiveMenu` surfaces that sentence through the CLI's existing error path (exit code 2), which was the de-facto status quo expressed as a build failure.
  - Tests: menu tests (if any touch the poll) stay green on darwin AND linux; the CLI's zero-arg windows behaviour is asserted only at the compile level (Item 4).
  - NOTES (2026-07-29): each per-OS file carries a **second** seam function beside `pollStdin(timeout) bool` — `requireInteractiveMenu() error` (nil on darwin/linux, wrapping `ErrUnsupported` on windows), called first in `RunInteractiveMenu`, exactly as Item 1 needed `requireProcessControl`. `pollStdin` cannot carry the refusal itself: it is called from `readKeyTimeout`, which returns a `keyCode` with no error channel, so a windows refusal there would spin the menu instead of surfacing a sentence. The windows message is the item's sentence with the sentinel wrapped onto it (`the interactive menu is not supported on windows: %w`), so `errors.Is(err, ErrUnsupported)` holds.
  - NOTES (2026-07-29): the item's "(exit code 2)" is wrong about this repo — the CLI's existing zero-arg error path is `cli.go:68-73` and returns **3**. Left unchanged: it is the path the item asks the sentence to travel, and changing the code would change darwin behaviour for every menu error.
  - NOTES (2026-07-29): the mandated file names carry Go's implicit filename constraints, so the package's platform set is now exactly darwin/linux/windows — other unixes (e.g. freebsd), which used to compile the BSD-form poll in `ui.go`, no longer have a `pollStdin`. That matches ADR-0012's three-platform contract and Item 4's GOOS matrix.
  - NOTES (2026-07-29): verified with **no overlay** — `GOOS=linux|darwin|windows go build ./...` all clean, `go vet ./...` and `go test ./...` green natively on linux (first native pass without an overlay; Item 4 records the `make` target). `GOOS=windows go vet ./...` still fails only on test files (`server_test.go:1594` `Setsid`) — Item 4's territory.

## Part B — Facade additions

- [x] **3. Two sentinels: `ErrUnsupported`, `ErrStartupTimeout`** — ✅ DONE (2026-07-29) — `internal/launcher/` + `launcher/launcher.go`, `launcher/doc.go`

  - Tests (`launcher/launcher_test.go`): `errors.Is` crosses the boundary for both new sentinels — the timeout one via the existing httptest stand-in forced to stay unhealthy with a shortened wait if the 30 s const is reachable in test, else via the internal error constructor (document which); the unsupported one unit-level on unix by calling the windows constructor directly (the sentinel, not the stub, is the contract).
  - NOTES (2026-07-29): the timeout test drives the **real** wait loop per the owner's decision — `internal/launcher/server_test.go`'s `TestLoadProfile_StartupTimeoutIsErrStartupTimeout` runs production `loadProfile`/`loadProfileManaged` against a never-healthy httptest stand-in, with only the wait window injected through the **existing** `activationOps.waitHealthy` seam (no new production seam was needed), and asserts `errors.Is(err, ErrStartupTimeout)` plus the unchanged PID/log-path message. It is in `internal/launcher` because no facade verb reaches a startup timeout without forking a real managed server.
  - NOTES (2026-07-29): the facade-side boundary proof is sentinel identity against the core values, in a new same-package file `launcher/launcher_internal_test.go` rather than in `launcher/launcher_test.go` — that file is an external test package on purpose (client-visible surface only), so it cannot import `internal/` to compare the values, and neither sentinel is reachable through a facade verb on unix (`ErrUnsupported` only ever surfaces from a windows build). Item 1's windows constructor therefore is not called from a test here.
  - NOTES (2026-07-29): verified on linux with a `-overlay` standing in for Item 2's `ui.go` fix (`go test ./...` cannot build natively until Item 2 lands); `GOOS=darwin go build ./... && go vet ./...` clean.
