---
title: "Flagged ambiguity: \"backend\" survives only on a transient field, and no LLM Server or Profile is ever the \"current\" one"
---

- The Go interface is `LLMServer` (renamed from `Backend` in 1.3.0) and the config key is `servers:`, both aligned with the domain term **LLM Server**. The word *backend* still survives on the transient `RunningInstance.Backend` field — a per-instance snapshot rebuilt from live probes on every command and never written to disk. The launcher persists no state: there is no on-disk state struct or schema, and instance identity is derived live from the `host:port` each server binds (see ADR-0006 and ADR-0007). Legacy `state-*.json` files written by pre-live-derivation versions are best-effort deleted on startup and carry no meaning.
- There is no global "active" or "current" Profile or LLM Server. Each running LLM Server has its own active Profile/Model (derived live by probing that server, not stored anywhere), but the system never picks one as canonical. When an action could apply to several running LLM Servers, the user selects which one — in the CLI via an optional argument (`llama-launcher stop [target]`, `llama-launcher unload [profile]`), in the TUI via a sub-list. When only one is a valid target, selection collapses to a single auto-resolved option. Avoid "active server," "primary server," "current server" as cross-cutting terms.
